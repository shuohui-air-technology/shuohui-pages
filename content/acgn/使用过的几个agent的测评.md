## 1. CodeWhale

推荐指数：(3/5)

我最早使用的 agent（如果不算上 Kimi 的 Computer 功能的话），来自 Hmbown 的项目：[CodeWhale](https://github.com/Hmbown/CodeWhale)。（deepseekTUI（后更名为 CodeWhale）。）

![CodeWhale 项目截图](/images/20260814-172422.png)

我了解到这个项目，是由于那段时间 V4 刚刚出来。那时候，V4-Pro 作为一个拥有百万上下文窗口的 agent，却没有对这个功能进行原生优化的 agent 框架；而 CodeWhale 在当时则是较早出现的、针对 DeepSeek-Pro 的长上下文窗口以及其他机制进行优化的项目，使得用户可以获得较为接近原生的 agent 使用体验。

我当时抱着学习的心态使用了 CodeWhale，并做了 [AIGC Humanizer ZH](https://github.com/shuohui-air-technology/aigc-humanizer-zh) 作为我的练手项目。

下面是在这个项目的过程中，我可以感受到的 CodeWhale 的一些优缺点。这是大致半年前的使用体验，由于该项目仍在持续更新，我无法确定现在的情况。

### 优点

- 由于 CodeWhale 是针对 DeepSeek 进行专门优化的，这使得它的缓存命中率相当高，并且对 Prompt Caching（前缀缓存）的利用相当优秀。
- CodeWhale 完善的安全策略和沙箱环境，有效减少了 agent 本地化运行初期经常被诟病的乱删文件导致不可逆损害的现象。在我的实际使用中，没有出现过任何负面性质的文件删除操作。
- 得益于 CodeWhale 基于 Rust 开发的这一特点，它在资源占用方面尤其轻量。对我个人而言，这种轻量化的使用体验是一个很大的加分项。

### 缺点

- 有趣的是，CodeWhale 完善的安全策略对我来说也是它的缺点之一。在我的 Mac 运行时，它总是会提醒我“没有权限调用 shell 命令”。在我明确要求它可以使用对应工具时，它仍然由于置于 prompt 前的仓库宪章（`constitution.json`）而频繁拒绝修改自身的配置文件。我不确定这是我个人的技术问题，还是开发者有意为之的设计，但我使用的其余 agent 确实从未出现过类似的权限问题。
- CodeWhale 在我使用的时候还有一些非常影响使用体验的问题：它原生的 memory 功能离奇地不好用。我经常要求它在一段对话完成之后将对话内容写入 `memory.md` 文件，但是它经常在下一次对话时无法自主读取 `memory.md`；而且似乎有一些时候，它会写入与项目无关的记忆，而与“我”有关。我阅读后发现这些来源于我的桌面文件中的信息，它可能更倾向于试图描绘用户画像，而不是我希望的项目记忆。这导致了我即使明确要求其写入记忆，最后仍然导致了项目进度的丢失。并且 MCP 以及其安装的 skill 也存在类似的问题：它在重启对话后经常丢失这些功能的具体列表，必须在我提醒后才能找回（但不排除我安装的方式存在问题）。

## 2. Trae（CN 版）

推荐指数：(4/5)

![](/images/20260819-015027.png)

作为字节跳动旗下的一款 agnet 产品，我认为 trae 可能是最适合新手/小白进行使用的 agent,它几乎没有使用门槛，并且很多时候几乎是免费的（以前trae 是免费的，充值仅能用于减少排队时长，但最近它引入了积分制，但似乎逐渐有了付费使用的框架），我之前有一些冗长的文书编辑工作就会在晚上睡觉前交给 trae，让它帮助我完成编辑，而我也显然不需要在意它完成任务所使用的时长

### 优点

- 正如人们说的，“我能用到的，才是好的”

在相当多人无法使用 vpn 以登录 github 或者使用如 codex,claude code 这样的 产品，可以直接下载的 trae 极大程度的降低了使用它的门槛，这是它最为显著的优点

- 它便宜，甚至很多时候是完全免费的，这几乎是我使用它的最大原因，并且这也使得我容易向他人推荐这一产品，因为人们常常不愿意为了自己不了解的东西花一笔钱，所以很多时候，trae 可以是人们了解 agnet 这一形态的好方式
- trae 内置有 agnet 操作浏览器的功能，这对很多情况下的自动化工作是一个显著的加分项

### 缺点

- trae 是不支持调节模型的思考强度的，这使得我明显感觉到 glm 5.2 的模型在有的时候表现的与我在 opencode 中使用的 glm5.2 的模型大相径庭，我不认为是它们暗中调换了模型，但似乎它们确实没有将模型的思考强度调到一个可以充分发挥模型性能的档位
- trae 的工作区是一个糟糕的设计，我常常要求它读取“我的整个桌面以寻找某个文件”，但它总是由于某种设计，只读取了极少数的文件（我确定我使用的本地的工作环境并且没有限制它的访问权限），并且它总是将生成的文件置于一个冗长的文件夹的嵌套结构下

似乎这种工作区的设计也影响到了 skill 或 mcp 服务的安装，我在一个对话中要求它安装的skill，很多时候会因为它每个对话使用分割的工作区的设计而直接失效

- 它无法自主显示上下文窗口的占用情况
- 还有一个糟糕的部分：

它的上下文压缩效果似乎很差，我有一次在使用 ds-v4-flash 模型执行一次任务时，由于上下文窗口的问题，它开始循环性的执行上下文压缩，而没有实际的执行任何任务，ds 模型仅仅是在继承了被压缩后的对话内容，在执行了几步后，又陷入了上下文压缩并损失细节，再执行的死循环中

## 3.OpenCode

推荐指数：（4/5）

![](/images/20260819-022807.png)

opencode 在很长的一段时间中都是我最喜欢的 agent 工具，其在侧边列出结构分明的文件结构，有着黑白分明，简洁的UI设计
我使用的是 opencode 的旧版界面，它有效的教会了我 agent“先规划明确需求，再执行”的这一普遍的使用准则
在 plan 模式下，agent是只读的，而在其他的 agnet中，使用/plan 调用的计划模式的 agent 几乎都是可以轻易的越过权限，而直接在 plan 模式就越界进行部分的编辑工作
